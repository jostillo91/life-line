# Architecture

React and TypeScript render small domain-focused UI components. Dexie provides IndexedDB tables and is isolated in `src/db.ts`; the interface reads and writes through this boundary. Domain types are in `src/types.ts` and timeline ordering/date labels are in `src/date.ts`.

## Installable app and offline shell

`vite-plugin-pwa` generates the production manifest and Workbox service worker from `pwa.config.ts`. `PwaStatus` registers it only in production, displays connectivity, offers installation only after a supported browser install event, and handles explicit update approval. Ordinary Vite development has no worker. Serve the production build over HTTPS (localhost is suitable for testing). Vite base, manifest identity/start URL/scope, registration and navigation fallback use the same normalized base directory; local development defaults to `/`, while Pages uses its repository subpath. The normal web app still works when workers/install prompts are unsupported. Icons reuse the existing green/cream timeline favicon, with 192/512px, maskable and Apple PNGs; `tools/generate-pwa-icons.ps1` regenerates them. Light appearance, launch background, viewport-fit and safe-area padding preserve the current layout, including capture, dialogs and lightbox.

The generated precache is application-only: root HTML, hashed JS/CSS (including all lazy views and the map worker), bundled fonts if present, branding icons and manifest. Root navigation uses the precached app shell rather than network-first HTML, keeping a coherent version until an approved update; non-root navigation and `/api/` never receive the app fallback. There are **no runtime caching routes** for API, geocoding or tiles. Workbox's root navigation route serves only the static shell. Memory text, archive JSON, backups, originals, thumbnails, GPS and AI responses never enter service-worker Cache Storage. Dexie/media storage and local editor/capture drafts remain unchanged; no schema, parallel archive or binary duplication is introduced. Existing remote Google Fonts are not precached; offline typography uses the existing system/serif fallbacks. See [Vite PWA precaching](https://vite-pwa-org.netlify.app/guide/service-worker-precache).

After the initial successful installation of assets, a fresh app launch can browse Timeline/Unsorted/entities, capture/edit, inspect History, open local media, run keyword search, and create full/encrypted backups or restore locally selected files without the app server. `networkState.ts` subscribes to browser online/offline events. Remote Assistant/embedding/Ask/session and address-lookup boundaries refuse network calls when offline; sources and keyword retrieval remain local. Existing semantic vectors are retained, and remote-dependent indexing/query actions explain connectivity requirements. Reconnect refreshes provider status, never automatically starts a paid query/indexing run. Life Map and Place pickers remove their network map instance while offline; stored coordinates, Place/Memory/media lists and manual coordinate editing remain usable. No regions/tiles are precached. A browser's online signal does not prove a server is reachable: normal provider error handling still applies when connectivity is reported but requests fail.

Updates use prompt mode, hashed/revisioned resources and established Workbox cache cleanup. Waiting workers do not activate automatically. Returning online or focusing checks for a worker update without an offline retry loop. `Update when ready` requires explicit approval and refuses reload with an open dialog/editor/capture, an archive operation, focused text input or tracked pending editor save. Close/save uses existing autosave/draft behavior; the reload guard is checked again during worker activation. Approval in another window never reloads this window. Close other app windows before applying an update to avoid an old window needing a lazy chunk removed by a newer deployment. Do not deploy hashed assets with premature deletion; retain the previous release's files while old clients remain open. Serve `sw.js` and manifest with revalidation, not long-lived immutable caching; hashed assets may be immutable. No push, background/cloud sync or service-worker archive writes are present.

Backup & Restore reuses storage estimates/status and offers a user-initiated persistence request only where supported. Granted, denied, unavailable and failed requests are distinct, with no automatic nag/retry. Persistence reduces eviction risk, not loss from clearing site data, device loss or browser limitations. Installation does not replace regular full backups. Browser profiles/origins remain separate local archives; moving to another hostname or browser does not migrate data automatically.

Validation: run the normal frontend/server TypeScript checks, production build and full test suite, then `pnpm check:pwa` to inspect the actual generated manifest/icons/worker and verify every lazy/static asset is included and every precached URL is application-only. Focused tests cover metadata/icons, connectivity/install/update UI, pending-save and cross-window reload guards, persistence outcomes, zero-fetch offline providers, vector preservation/reconnect, and local capture/edit/history/media/full ZIP/encryption/restore. Real browser service-worker activation and device installation remain integration checks, not mocked worker-internal unit tests.

Navigation remains existing React view state, not URL routes. Launch, refresh and installation always use the app base directory; Memory/detail/editor transitions do not create deep paths. No router, `404.html` redirect or arbitrary SPA fallback is added. Manifest, icons, scripts/styles and worker resources are prefixed consistently. The navigation precache fallback serves only the app-base URL, never an API or arbitrary nested path. Application-only caches, optional install and safe-update guards are unchanged. Pages does not retain every historical release asset: close other app windows before approving an update, as documented above.

Pages hosts no Node/API/session/embedding/Ask server. The Pages build explicitly disables remote AI and clears its endpoint and optional geocoder key, even if local environment variables were configured; unavailable UI remains graceful. No credentials, exports, IndexedDB records, media originals, GPS history or derived vectors belong in the static artifact. Development fixtures are DEV-only and a newly initialized production archive is empty; existing records are never erased or reseeded. The audit rejects obvious private artifacts and known credential patterns, but is not a guarantee against every possible secret format.

The hosted HTTPS origin is different from localhost. Each device/browser keeps its own local IndexedDB archive; nothing automatically uploads, migrates or synchronizes it. To move an existing archive, export a full ZIP or encrypted backup from the old installation, keep a durable copy/password, and explicitly restore the selected file in the hosted installation. Safari and a home-screen installation may not share storage; install first and restore in the installation you intend to use. GitHub Pages is application hosting, **not cloud backup**.

## Explorable Timeline

`timelineLayout.ts` is the pure presentation boundary: UTC calendar parsing, uncertain-date spans, extent, focal position, zoom duration, filter-aware clustering, date/era label tracks, density bins, jumps, and completed-birthday ages. It does not write canonical Entries. `TimelineView.tsx` delegates selection and confirmed date changes to the existing App/detail/dialog/undo flow. No provider or API is used.

Scales are Entire Life (extent including eras, birth date, today, and future entries), Decades (20 years), Years (2 years), Months (90 days), and Days (7 days). Durations are capped by the life extent, which has a minimum one-year duration. Switching scales preserves the focal instant; Fit entire life intentionally recenters. Jump accepts a four-digit year (its midpoint), an exact date, or an era's midpoint. The UTC calendar axis adapts label frequency to width. Age means completed birthdays at the labeled instant; before birth, or without a configured birth date, it is omitted. February 29 birthdays advance on March 1 in non-leap years.

Intersecting intervals enter screen-width buckets (~230px). Wide scales retain the highest-importance (4+) Memory per bucket separately; others group. Close scales show up to two separate Memories per bucket, grouping the rest. Exceptionally dense milestones may still group rather than overlap. Every matching canonical Memory appears exactly once in the visible layout, including ranges whose midpoint is offscreen. Cluster counts represent Memories and unique referenced media/images from metadata only; shared photos count once per cluster. Activation centers the cluster period, steps inward one scale, and reveals a 30-per-page list using the existing Memory detail. No ordinary Memory is discarded. Unplaced lists are also paginated.

Exact dates occupy a day. Month/year dates occupy the full period; ranges cover both endpoints (including the last full month/year for partial endpoints). Seasons use explicitly disclosed northern meteorological quarters, with winter extending into the following year; an unnamed season uses the full year, not an invented summer. Approximate dates keep their supplied anchor/granularity with a fuzzy visual and approximate wording; the glow is not a confidence interval. Incomplete/invalid spans, age-only, and unknown dates receive no invented position. Labeled date tracks prevent long ranges from obscuring soft markers. Life Eras use separate labeled bands; open ends extend to the archive extent and overlapping labels occupy separate lanes.

The 60-bin overview shows filtered archive density, not personal importance, and the current viewport. Its native range control supports click/drag and keyboard navigation. Horizontal wheel/trackpad and Shift-wheel pan; vertical wheel remains page scrolling and Ctrl/Command-wheel remains browser zoom. Horizontal-dominant background pointer drags pan; touch drags can start over cards while taps still open them. Vertical touch motion remains page scrolling. Explicit controls are touch-friendly. Focused-canvas arrows pan and +/- zoom; Memory/cluster buttons support Tab/Enter. Reduced-motion styling disables transitions. No pinch gesture is required or implemented.

Months/Days draggable cards and Move date buttons open the unchanged confirmation dialog with original precision/confidence. Drop never guesses an exact target date. App owns commit and inverse undo. Coarse dragging is disabled. Local keyword and Person/Place/Tag/type/year/era filters run before clustering; year/era overlap uses precision-aware spans. Filtered counts exclude hidden Memories. Focal date, scale, and filters survive view switches in module session memory (like Life Map), not URLs or backups.

Memoized filtering/intervals and viewport culling bound rendered cards to three per screen bucket. Only visible individual cards request thumbnails; density loads no binary. Cluster/unplaced lists mount at most 30 items per page. Layout is linear plus per-bucket sorting, not a worker/spatial index. `timelineFixture.ts` supplies 2,000 deterministic metadata-only Memories and nearly 12,000 referenced photos, broad past/future dates, all precisions, and ranges. DEV-only `?timelineFixture=empty|small|large` loads `TimelinePlayground` instead of App, exercising the real Timeline/detail/date dialog with disposable in-memory state, never production seeding or archive writes. Preview photo binaries are disabled. Production builds eliminate this entry path.

Dexie schema 7 adds `archiveSettings` keyed by `profile`. Optional `Archive.profile.birthDate` is user-owned metadata included in JSON, ZIP, and encrypted backups. Schema-6 records upgrade unchanged with no default birth date. Archive v1 remains compatible with files lacking a profile. Replace restores the incoming profile (or clears it if absent); Merge keeps a configured local birth date, adopting incoming metadata only when local birth date is absent. Full validation checks its calendar value, and metadata participates in the restore transaction. Timeline positioning/cluster state is never persisted.

## Archive, editing, and media

### Quick Capture

`QuickCaptureView` is a minimal focused dialog, not a second editor or notes inbox. App owns opening/closing and the global Ctrl/Cmd + Shift + M listener; the listener ignores editable controls, repeated keystrokes and other open overlays/dialogs. The story textarea receives initial focus, Tab stays within the capture, Escape/backdrop/Close preserve meaningful work, and Ctrl/Cmd + Enter saves. Optional title/date/attachments are behind one disclosure. Mobile sizing keeps text readable and primary actions touch-friendly without nested dialogs. After save, Done dismisses or Open full editor hands the same canonical Memory to `MemoryDetailView`/`MemoryEditorView`.

`quickCaptureDomain.ts` provides ordinary Entry drafts, date shortcuts, validation, recovery and one-submission locking. A single versioned local-storage draft per archive (`life-line:quick-capture-draft:<database name>`) is synchronously updated on edits and flushed on pagehide/unmount. Opening an empty capture creates no canonical record or revision. Resume preserves identity, text, timestamps and media IDs; Discard removes only that draft. It is separate from the full editor's unfinished-new-memory draft so neither overwrites the other. Browser quota/unavailable storage produces an explicit warning; unsafe closure is blocked when meaningful work cannot be preserved. A canonical save can still be attempted. Local drafts are not durable backups and cannot survive cleared browser storage. Concurrent tabs are not a coordinated multi-draft inbox (the last local draft write wins).

Default event date is unknown, irrespective of recording time. Today/Yesterday use local calendar dates; This year uses existing year precision. Approximate stores only the supplied year with approximate confidence, displays “About 2012”, and the existing Timeline treats it as an uncertain year span. A configured archive birth date enables approximate age input without deriving a day/year. Unknown and age-only captures naturally enter existing Unsorted Memories. Changing date never changes the original creation/record timestamps.

Compact `AttachmentPanel` delegates serial local imports to `quickCaptureMedia.ts`, reusing `saveMediaFile` and thumbnail generation. Import/preview failure is reported independently of the text; failed thumbnails retain successfully stored originals. Save/close is locked during import, and canonical submission is synchronously locked against repeated clicks. `quickCaptureService.ts` validates available attachments and uses the existing transactional `saveMemory` boundary. No fake initial history is created, while later full-editor changes preserve the captured baseline. Imported but discarded/detached files remain normal unattached Media available in the library and full backups.

Saved captures are immediately normal keyword/filter input and normal candidates for explicitly enabled semantic indexing. Capture never enables indexing or calls AI, remote authentication, map/geocoding, or cloud services. Capture/recovery/local attachments work without internet; the production PWA shell now also supports offline cold starts after initial asset installation (see above). The body uses a single controlled draft-update path which future voice input can populate; speech recording/transcription is deliberately not implemented.

Focused tests cover canonical saves, dates/timestamps, recovery/discard, missing/import/preview failures, double-submit/retry, shortcut guards, pending-save attachment locking, existing-editor handoff, revision baselines and no-provider operation. Browser checks use the existing isolated `?revisionFixture` archive, never the personal diary: desktop/body-only/unknown capture, close/refresh recovery, 390px mobile layout, local image/failed-preview safety, immediate keyword search, ignored shortcuts in search input, approximate-year full-editor editing, and capture/save/Unsorted with the frontend server stopped after loading. Original import failures are deterministically exercised in tests rather than exhausting browser quota. The full suite passes 222 tests in 36 files (23 Quick Capture tests); frontend/server TypeScript and production build pass. Existing large-chunk warnings remain; no lint script is configured.

### Durable Memory History

`memoryRevisionDomain.ts` owns explicit canonical snapshots, meaningful field comparison, restore/reference filtering, bounded line diffs, and archive validation. `memoryRevisionService.ts` atomically saves a previous snapshot and the current Entry through the existing Dexie database. Entries remain canonical current records, not event-sourced projections. `MemoryHistoryView` is a read-only, newest-first, 20-per-page dialog opened from detail or editor; opening History flushes existing editor changes first. No history snapshots are queried by normal `archive()` loads. Backup/JSON callers explicitly request `archive({includeRevisions:true})`, which reads canonical data and history in one read transaction.

**Revision vs draft vs undo:** unfinished new-memory drafts stay in local storage; existing-memory autosaves keep the latest work in IndexedDB every 650ms. Durable revisions preserve meaningful previous saved states across refresh/restart/backup, while the existing seven-second undo remains a convenience only. Schema 8 adds `memoryRevisions` without rewriting old tables or generating synthetic history. New and bulk-created memories have no invented prior state. A saved memory receives its first baseline only when its user-owned content actually changes. Identity, `createdAt`, `recordTime`, and `updatedAt` do not trigger content revisions.

**Checkpoint policy:** the first changed autosave in an editor session/five-minute window captures the state before that change. Further autosaves, Save, and Close in that same window update only the current Entry. A changed save in a later window or new editor session captures another prior state. Windows are measured from session start, not each keystroke. Save/Close/History/date-review flush and serialize pending editor saves; opening history closes the editor to avoid stale autosaves racing restoration. Each checkpoint's summary describes its triggering change; comparison with current shows all subsequent differences. Date moves, undo, accepted assistant changes, bulk attachment operations, entity detachment, and restores receive explicit sources. Assistant acceptance flushes prior typed work, starts a new checkpoint segment, and subsequent ordinary edits start another segment. Pending/rejected suggestions never write history. An intervening discrete operation breaks editor coalescing; unchanged saves create no checkpoint and leave `updatedAt` unchanged.

**Restore:** selection only previews snapshots. An explicit Restore action opens a confirmation before any write. The service re-reads current memory/revision/references in a single transaction, preserves the pre-restore current content as a new `restore` revision, then replaces user-owned fields while keeping current ID, original creation timestamp and record timestamp. `updatedAt` advances monotonically; all newer/older revision records remain untouched. Restoring already-matching meaningful content is a no-op. To undo later, restore the pre-restore version from History; no temporary undo is required. Missing People, Places, Tags, Media and related-memory IDs are displayed as unavailable, omitted from the restored current record, and explicitly reported. Historical snapshots retain these IDs. No binary or deleted entity is recreated.

**Retention/deletion:** normal Delete sets optional `deletedAt` on the existing canonical Entry without changing its content, relationships, identity or creation timestamps. Final/prior revisions remain. Seven-second Undo uses the same local restoration service as Recovery Center, guarded by the deletion timestamp so stale Undo cannot revive a re-deleted/purged memory. Default archive reads return only live records; explicit complete exports request deleted records and history. Recovery Center under Backup & Restore uses a reactive newest-first list, read-only content/media previews, and Restore with safe missing-reference warnings. Deleted related-memory links remain stored but cannot navigate through ordinary live views; restoration makes valid links usable again.

Permanent deletion is separated below Restore, requires the exact typed `DELETE N` confirmation, and rechecks target IDs/deletion timestamps inside a transaction. It removes canonical targets, all owned revisions and vectors, and safely detaches incoming related references (checkpointing changes to live records). Empty Trash snapshots and confirms the displayed count; changed targets abort the whole operation. Neither action deletes Media metadata or binaries. Deleted memories no longer count as live attachments in Media Library; explicitly deleting an unattached file can leave unavailable references which recovery reports rather than recreating bytes. No expiration, automatic pruning or retention cap exists. An internal initialization marker prevents intentional empty archives being reseeded. Replace explicitly replaces the entire local archive including Recovery Center/history; Merge retains local records. Stale editors cannot recreate permanently deleted records or edit soft-deleted ones.

The complete suite has 256 passing tests. The prior physical-phone PWA checkpoint is accepted as passed per the user's instruction.

**Backup/search/storage:** archive ZIP/JSON v3 (schema metadata 8) includes deletion metadata and complete history; ZIP manifest counts include deleted memories. Legacy v1/v2 remain readable with no invented history/deletion. Encrypted container v1 wraps the complete v3 ZIP unchanged. Version 3 prevents older readers silently presenting deleted records as live. Merge remaps incoming revision IDs on collision, owners and snapshot references consistently with canonical ID maps, and deduplicates identical history. Missing incoming historical/deleted references cannot bind to unrelated local records sharing their IDs. Conflicting canonical records, including different deletion states, remain separate under the preservation-first policy: local live records are never overwritten with incoming deleted copies, and incoming live copies do not silently revive local trash. Restore validates timestamps/snapshots before destructive commit. Keyword/semantic filtering, indexing, entity lists, maps and Ask evidence exclude deleted records even when passed a complete archive. Deletion removes vectors; in-flight indexing rechecks current state before writing. Restoration leaves the memory pending explicit indexing, never calling a provider itself.

Only current Entries feed Timeline, keyword/semantic documents and Ask evidence; no historical text is sent automatically to any AI provider. Snapshots are text/metadata with stable media references/order, not copied blobs. Growth is unbounded meaningful history subject to browser quota and existing backup memory/100MB structured-data inspection limits; back up regularly. Body comparison uses a line-level LCS up to 100,000 line-pairs/combined characters, falling back to full read-only previews for larger stories. It is intentionally not a word-level source-control interface.

DEV-only `?revisionFixture` mounts `RevisionPlayground` with a separate persistent `life-line-revision-fixture` database. It uses the real App/editor/history and provides a real ZIP backup + Merge roundtrip check, without reading or modifying `life-line-diary`. Refresh retains fixture history. Production eliminates both the fixture entry path and alternate database name. Desktop/390px manual checks cover repeated autosaves, close/history, old/current comparison, Timeline date movement, confirmation/restore, pre-restore preservation, refresh, and small-archive ZIP/Merge. Automated tests additionally cover encryption, Replace, schema-7 upgrade, ID/reference collisions, missing references, search isolation and deletion/undo.

The Timeline uses a horizontal, viewport-sized chronological canvas. Date-less and age-based items remain unpositioned and available in Unsorted Memories and a paginated unplaced list. `mediaIds` reference independent local Media metadata and binaries.

Editor drafts use local storage only while a new entry is unfinished; existing entries are debounced into IndexedDB. The small undo surface stores a reversible action in UI state. Entity deletion removes references from live entries transactionally before removing the entity; deleted entries retain unavailable references until recovery reports omissions.

Timeline drag/drop opens a compact confirmation step rather than guessing a date. That dialog starts from the existing uncertain-date model and only updates event-date fields. Its inverse action is stored for lightweight undo.

Media metadata is held in the Dexie `media` table, separate from entry records. Binary bytes use the media-storage service and a separate `mediaFiles` table keyed by stable storage keys; writes save bytes before metadata in one transaction. The service checks browser quota and exposes object-URL lifecycle helpers. A future OPFS/cloud provider can implement the same service boundary.

The storage service now owns browser image thumbnail generation and preview URL lifecycle. Thumbnails are separate binary records; original media is never resized or rewritten.

Bulk photo import is a review-first pipeline. Files are hashed and read locally, then EXIF, filename, and file-modified evidence becomes a date suggestion in the queue. Nothing is persisted until the user starts import, and no Memory is created or redated unless the user explicitly chooses a timeline relationship. Imports use the existing media storage transaction and thumbnail service rather than a parallel binary store.

Media schema version 3 indexes `contentHash` and `captureDate`. SHA-256 hashes prevent duplicate physical storage; legacy media without a hash is upgraded lazily when duplicate detection examines it. EXIF parsing uses the local `exifr` package and never sends image bytes, GPS, or camera metadata to an external service.

Media schema version 4 adds the optional indexed `placeId` relationship. GPS evidence remains in `photoMetadata`; a confirmed Media-to-Place relationship is stored separately and never implies an Entry-to-Place relationship. Removing a Place clears its Media and Entry references transactionally without deleting either records or files.

Location logic lives in `locationDomain.ts`. It validates WGS84 coordinate ranges, measures Haversine distance, groups connected photos within a 150-meter default radius, and uses an arithmetic latitude/longitude mean as the representative center for these small local clusters. Existing Places are considered within 200 meters; two candidates within 50 meters of each other are treated as ambiguous and no default is chosen. All calculations remain in the browser, with no maps, analytics, or reverse-geocoding requests.

Full backups use archive format version 3, independently of Dexie schema version 8, while reading legacy v1/v2 archives. `archiveFormat.ts` owns the manifest, validation, migration entry point, relationship checks, and merge ID remapping. `archiveService.ts` owns ZIP I/O, binary hashing, storage checks, staging, and transactional commit. The current ZIP layout contains `manifest.json`, `data.json` (including deleted canonical memories and durable revision snapshots), and opaque numbered files under `media/`; the manifest maps each file to its stable Media ID, original filename, MIME type, size, and SHA-256 hash.

Thumbnails are excluded because they are derived data. Their metadata pointers are removed during backup/restore and the existing thumbnail service regenerates them locally when previews are next requested. Originals are added without recompression and are always verified against SHA-256 before restore.

Restore validation occurs before user choices are enabled. Replace stages every incoming original in the temporary `restoreFiles` table, then swaps records and binaries inside one IndexedDB transaction; a failed commit rolls back instead of leaving a half-empty archive. Merge keeps local records, reuses binaries by content hash, preserves non-conflicting stable IDs, remaps conflicting IDs, and rewrites incoming relationships. ZIP construction currently finishes into a browser Blob, so very large multi-gigabyte archives remain subject to browser memory and download limits even though media entries are processed one at a time.

Encrypted backups are an optional wrapper around that unchanged ZIP. `encryptedArchive.ts` uses browser Web Crypto: PBKDF2-HMAC-SHA-256 with 600,000 iterations, a fresh 16-byte random salt, a non-extractable AES-256-GCM key, and a fresh 12-byte random IV. PBKDF2 avoids an additional Argon2/WASM dependency and works in the browsers already targeted by this local app. The password is used only in memory for the operation and is never saved, placed in the manifest, or sent over a network. A forgotten password cannot be recovered.

Encrypted container version 1 is independent of ZIP archive version 3 and Dexie schema version 8. Its binary layout is: 8-byte ASCII magic `LLBACKUP`, 1-byte container version, 1-byte KDF identifier (1 = PBKDF2-HMAC-SHA-256), 4-byte big-endian iteration count, 16-byte salt, 12-byte IV, and AES-GCM ciphertext with a 16-byte authentication tag. The full header is GCM additional authenticated data. The private manifest, structured data (including deleted memories/revisions), and original media all remain inside the encrypted ZIP payload. Restore detects magic bytes rather than relying on `.encrypted` or `.zip`, prompts for a password only for an encrypted file, and passes successful decryption through the same ZIP/hash validation and Merge/Replace pipeline. Standard ZIP v1/v2 archives remain readable.

Web Crypto AES-GCM operates on a complete buffer, so encryption/decryption of large archives needs additional browser memory beyond ZIP creation and may fail on memory-constrained devices. Final encrypted output is authenticated and compared with the source archive in bounded chunks before download. Cancellation is checked around browser cryptography operations, but an in-flight Web Crypto call cannot be interrupted. Processing is entirely local.

Life Map uses MapLibre GL JS in a lazy-loaded view. `lifeMapDomain.ts` derives one marker per coordinated Place from existing Place, Entry, and Media relationships, plus an optional unassigned-GPS Media layer. When a confirmed Place has no coordinate but an associated photo does, the marker uses that photo's GPS position as a clearly labeled display fallback without changing the Place record. Its year/range/Life Era filters are pure local calculations. MapLibre's GeoJSON clustering reduces overlapping markers at wide zoom levels; it is presentation-only and does not change the separate 150-metre Place Suggestions clustering in `locationDomain.ts`. Center, zoom, and filters live in session memory, not in the archive or IndexedDB.

`mapProvider.ts` isolates the base-map style. By default the map requests OpenStreetMap raster tiles with visible attribution; set `VITE_LIFE_MAP_STYLE_URL` to a compatible MapLibre style URL to use a different provider. Opening the map or coordinate picker makes tile requests that reveal the viewed area to that tile provider, but no names, stories, captions, photos, or exact archive records are sent. There is no device-geolocation request. If tiles fail, Place and Media data remain in local storage and can still be browsed in their normal views.

`maplibreSetup.ts` bundles MapLibre's worker through Vite's worker pipeline, so GeoJSON markers and clustering work in both development and production builds. MapLibre is lazy-loaded with the map/editor rather than included in the initial application view.

`reverseGeocoder.ts` is a separate provider boundary. A MapTiler reverse-geocoding adapter is available only when `VITE_LIFE_MAP_GEOCODER_KEY` is configured. A browser `VITE_` key is public at runtime, so use a provider key restricted to the app's origin and quota; do not use a secret server credential. The Place editor makes no lookup automatically: an explicit button and disclosure/Continue step precede a request containing only one latitude/longitude pair. Results are normalized into provider-independent address fields, cached locally at four-decimal coordinate precision, and rate-limited; the user must choose a suggestion and save the Place. The personal Place name is never replaced by a suggested address. No new Dexie version is needed because `Place.address` is an optional field in existing records and archives.

## Memory Assistant boundary

`assistantDomain.ts` defines the provider interface, task-specific request context, service, suggestion/provenance model, and explicit acceptance helpers. React uses that service through `MemoryAssistant.tsx`. `mockAIProvider.ts` remains deterministic and local. `remoteAIProvider.ts` implements the same interface over the narrow Life Line endpoint; no browser code imports the OpenAI SDK. The service's existing first-remote-request consent gate runs before the provider receives context, and the UI retains the context preview and Continue/Cancel choice. The optional remembered consent is only in local browser storage, not the archive.

The archive contains user-confirmed facts and source evidence. AI responses are always suggestions, never direct writes. The UI labels suggestions, keeps original prose next to draft prose, and requires an explicit Insert below, Replace text, Add this to my memory, or Accept action. Accepted changes in the detail view use the existing short-lived undo surface; the editing view uses its existing draft/autosave path. Dates are not applied by the assistant; a possible date can only open the existing move/confirmation dialog. People and Places can only link to existing records. Tag acceptance reuses normalized existing Tags or creates one through the existing Tag creation path. Unknown names remain unlinked suggestion text. Life Era suggestions are based on existing date ranges and are informational because Entries have no Life Era link field. Cautions about potentially conflicting dates do not resolve contradictions.

The context builder starts with only the selected memory and its date. Users can opt in linked related memories; People and Place names are limited to linked records or records whose names occur in the selected story. Other archive stories are excluded. Context is task-specific: media metadata is available only to question prompts when selected, not to organization/writing requests. Binary media is never included. Raw EXIF/GPS is excluded; exact confirmed Place coordinates require an explicit per-request checkbox. Long stories and related text are trimmed deterministically, with a 6,500-character serialized context ceiling. The preview displays categories, counts, trimming, and approximate size. A provider receives anti-invention instructions, not authority to edit the archive.

Suggestion records (including pending, accepted, rejected status, provider/model, timestamp, source memory ID, and context categories/related IDs) live only in the open assistant panel. Closing or refreshing discards them; they are not in Dexie or JSON/ZIP/encrypted backups. Explicitly accepted edits become ordinary canonical Entry/Tag changes and are included in backups; suggestion provenance is not retained after that panel closes. Draft conversation answers also remain disposable until the user explicitly adds them. Provider failures, cancellation, and timeouts leave the archive unchanged. This pass does not add image recognition, voice transcription, full-archive search, or autonomous editing.

### Private server-side OpenAI endpoint

The repository remains a static Vite frontend with a separate, single-instance Node HTTP API in `server/`. Vite's development proxy forwards `/api/memory-assistant` to `127.0.0.1:8787`. For production, run the API behind a standard HTTPS reverse proxy and either forward that path from the frontend's origin (preferred) or use a separate **same-site** HTTPS origin. This does not migrate the frontend to another framework. The API password protects only remote AI spending; it is not an account system or encryption/access control for the local IndexedDB archive or public static files.

The API never accepts an arbitrary OpenAI request. It validates the known Life Line task contract, including context size, candidate counts, and stable IDs. It uses the official OpenAI JavaScript SDK and Responses API, task-specific strict `text.format` JSON Schemas, low reasoning effort, no tools, `store: false`, and server-side output validation. `OPENAI_MODEL` is set only by the server operator and defaults to `gpt-5.6-terra`; `LIFE_LINE_AI_MAX_OUTPUT_TOKENS` can lower but not raise the hard 1,100-token ceiling (800 for non-writing tasks). No archive content is applied without the existing user acceptance flow.

#### Authentication and endpoint protections

`LIFE_LINE_AI_ACCESS_PASSWORD` is a long, unique **server-only secret** (16–256 characters). The user enters it in the Memory Assistant only when the live provider is selected. The API checks it with a timing-safe comparison and issues a random, server-validated, bounded-expiration cookie. The cookie is `HttpOnly`, `SameSite=Strict`, host-only, restricted to the AI path, and `Secure` in production. No password or OpenAI key is written to frontend JavaScript, IndexedDB, or LocalStorage. Sessions live in API process memory; a restart signs users out. Login attempts are limited by client address and globally. Remote AI requests require a valid session **and** an exact `Origin` match before provider invocation. A missing Origin on a write is rejected. CORS never uses `*`; it allows credentials only to the configured frontend origin. The browser can show ready, authentication-required, unavailable, or explicitly labeled development-mock status without sending memory text. `GET /api/memory-assistant/health` reveals only `{ "ok": true }`; authenticated `/status` and `/diagnostics` reveal readiness and aggregate request/token counters, not archive content or secrets. Cookie-based cross-site deployments are unsupported; use same-origin or same-site HTTPS.

AI responses carry `private, no-store` cache control, `nosniff`, frame denial, and a restrictive API content policy. Operational logs include only request ID, pseudonymous session ID, task, timing, outcome, provider request ID, and token usage. They never include archive stories, names, coordinates, prompts, drafts, passwords, cookies, or API keys. Client cancellation aborts fetch; server disconnect/timeout aborts upstream work where supported. The local archive remains usable if authentication expires, the API is offline, or OpenAI fails.

#### Configuration and deployment

The placeholder-only `server/.env.example` lists configuration; Node does **not** load it automatically. Run the API with Node 24 or newer and supply server variables through your host's secret/environment settings. Required in production: `NODE_ENV=production`, `LIFE_LINE_AI_ALLOWED_ORIGIN` as the exact HTTPS frontend origin, a unique `LIFE_LINE_AI_ACCESS_PASSWORD` (the example placeholder is refused), and `OPENAI_API_KEY`. Optional server variables: `OPENAI_MODEL`, `LIFE_LINE_AI_HOST` (default loopback), `LIFE_LINE_AI_PORT` (default 8787), `LIFE_LINE_AI_SESSION_TTL_MINUTES` (default 480; maximum 1440), `LIFE_LINE_AI_MAX_REQUESTS_PER_MINUTE` (default 6; maximum 60), `LIFE_LINE_AI_GLOBAL_REQUESTS_PER_MINUTE` (default 30; maximum 600), `LIFE_LINE_AI_MAX_CONCURRENT` (default 2; maximum 8), `LIFE_LINE_AI_MAX_BODY_BYTES` (default/hard maximum 10,000), and `LIFE_LINE_AI_MAX_OUTPUT_TOKENS` (default/hard maximum 1,100). Structured context is still capped at 6,500 characters; questions/suggestions and generated drafts retain their smaller validation limits. These limits are per API process; this design is for one private instance, not serverless replicas. A multi-instance deployment needs shared session storage and rate limits.

Build the static frontend with `VITE_LIFE_LINE_AI_MODE=openai`. Leave `VITE_LIFE_LINE_AI_ENDPOINT` unset for the preferred same-origin reverse proxy, or set it to the full API HTTPS endpoint on a same-site origin. Neither frontend setting contains a credential. Terminate HTTPS for both frontend and API at the host/reverse proxy; keep Node on a private interface where possible. Set `LIFE_LINE_AI_ALLOWED_ORIGIN` to the frontend's exact origin. `NODE_ENV=production` refuses non-HTTPS frontend origins and refuses the development mock provider. Real secrets belong only in the API process, never a `VITE_*` variable or committed `.env` file. The `.gitignore` excludes secret-bearing environment files.

For local mock-only UI development, run `pnpm dev` with `VITE_LIFE_LINE_AI_MODE` unset or `mock`; no API or password is needed. To exercise the authenticated API without a paid call, set a local `LIFE_LINE_AI_ACCESS_PASSWORD`, set `LIFE_LINE_AI_PROVIDER=mock` in the **development API process**, run `pnpm dev:api`, and run Vite with `VITE_LIFE_LINE_AI_MODE=openai`. For actual live local use, omit `LIFE_LINE_AI_PROVIDER=mock` and set `OPENAI_API_KEY` only in the API process. The mock server mode cannot start in production. Do not put the access password in a shell command recorded in history, a checked-in file, or a Vite variable.

Use a dedicated server-side OpenAI project/environment credential, monitor project usage, configure a spend alert or hard project spend limit, and rotate a key if exposure is suspected. OpenAI's [production guidance](https://developers.openai.com/api/docs/guides/production-best-practices) and [spend-limit guide](https://developers.openai.com/api/docs/guides/spend-limits) describe those controls. Life Line does not manage billing or keys automatically.

#### Deployment smoke checklist

1. With the production frontend and HTTPS API running, confirm unauthenticated AI POST returns `401`, wrong-Origin or missing-Origin write returns `403`, and health returns only `{ "ok": true }`.
2. Open a memory's Memory Assistant, sign in, and confirm it shows “Live assistant ready”. Check that the password is absent from the built JavaScript and browser storage; only the HttpOnly session cookie is present.
3. From an authenticated test client with the exact Origin, confirm an unknown task is rejected (`400`), a body over 10 KB is rejected (`413`), and repeated requests reach `429`. Confirm `/diagnostics` contains only aggregate counts/tokens.
4. In the UI, try Help me remember, Organize this memory, and Help me write. Confirm suggestions remain pending and no archive field changes until you explicitly accept or insert them. Reject or discard a suggestion and confirm the original memory is unchanged.
5. Sign out or let the session expire, then confirm remote AI asks for sign-in while local memories and edits remain usable. Simulate API/provider failure and confirm the draft and archive remain intact.

Automated tests use fake responses and spend no API money. A paid live smoke test is opt-in after a real server key is configured; it was not run as part of the normal suite.

## Search and semantic index

Search is a lazy-loaded view with always-local keyword matching and optional semantic matching. Both modes return existing Memories and open the original detail view; they do not generate answers or change archive facts. Year range, Life Era, Person, Place, Tag, and entry-type filters run locally. Keyword search remains usable when the AI server is offline or semantic search is not enabled.

Semantic search requires a separate, explicit archive-level opt-in and a separate Index action. For each Memory, `semanticSearch.ts` constructs bounded text from its title, story, date/Life Era context, and linked People, Places, and Tags. It excludes media binaries, raw GPS, EXIF, unrelated memories, and draft/assistant text. The disclosure appears before enabling. Queries are sent to the configured embedding provider only when the user submits a semantic search; vector comparison and ranking happen in the browser. The deterministic development mock makes no network or paid AI call. Production semantic search uses the same authenticated, exact-origin, server-side API boundary as Memory Assistant; no OpenAI key enters the browser. The server accepts only bounded embedding documents or a bounded query, applies shared per-session/global/concurrency limits, and records aggregate usage rather than content. Configure `OPENAI_EMBEDDING_MODEL` (`text-embedding-3-small` by default, or `text-embedding-3-large`) and `OPENAI_EMBEDDING_DIMENSIONS` (256 by default, maximum 1536) on the server. Model/dimension changes mark existing vectors for rebuild.

Dexie schema version 6 adds `semanticVectors` and `semanticSettings` without changing canonical records. The index stores one numeric vector per Memory, its SHA-256 content fingerprint, model, dimensions, and index version. On demand, the planner compares these fields, skips unchanged Memories, updates only changed ones in batches of at most two, and removes orphan vectors. A related Person/Place/Tag or Life Era rename changes the derived fingerprint only for affected Memories. Failed batches stay pending for retry; there is no automatic paid re-indexing. Users can cancel indexing, rebuild, or delete only the derived index. Semantic search shows only vectors compatible with the current model/dimension/version; query results are leads to inspect, not provenance or factual claims. Very large archives may need several indexing runs because the server's default request rate limit also applies to embedding calls.

Ranking uses local cosine similarity with a fixed 0.3 boost when the complete query occurs in a Memory title, plus a small capped keyword boost (at most 0.1) from title, story, and context matches. Ties use stable Memory IDs. Raw similarity numbers are not shown as factual confidence.

Vectors, semantic opt-in/settings, and indexing progress are local derived state, not archive-format v1 data. JSON and full ZIP/encrypted backups exclude them. Both Merge and Replace restore invalidate local vectors transactionally; memories are never removed to repair the index. After restore, semantic indexing must be explicitly run again. Opt-in remains local to the browser and does not transfer with a backup.

For production, build with `VITE_LIFE_LINE_AI_MODE=openai`, run the authenticated API over HTTPS, and configure its server-only OpenAI key and embedding settings. The embedding request uses the official OpenAI embeddings endpoint through the server SDK. A live embedding smoke test incurs API usage and must be deliberately opted into; normal tests and development mock do not use a paid key.

## Ask Life Line

Ask Life Line lives inside Search and reuses its local semantic index, embedding provider, keyword score, and structured filters. A question first resolves exact known Person, Place, Tag, Life Era, and year hints locally; a unique, dated move Memory can also anchor a conservative before/after year filter. Retrieval ranks matching canonical Memories using existing hybrid semantic/keyword results plus title matches. Conversational filler is removed from semantic queries, and an unstructured candidate needs a keyword hit or a minimum 0.34 hybrid semantic score; this simple threshold avoids weak mock matches but may miss some genuinely relevant Memories. Without an enabled/current semantic index, Ask uses keyword and structured matches only; it never enables indexing automatically. Retrieval is repeated for each follow-up, optionally combining a referential follow-up with the previous question for hints. Conversation turns remain disposable React state (up to six recent turns), outside IndexedDB and every backup. New question clears them.

`askDomain.ts` selects at most five evidence records and sends only their stable Memory IDs, title, bounded story excerpt, original event-date fields plus formatted label, linked People/Place/Tag names, and entry type. It excludes raw GPS, media binaries, backups, and unrelated records. The Ask UI displays a Sources being shared preview, names and approximate context size before a separate Continue action sends the question/evidence to the answer service. The remote mode reuses the existing AI session and local remembered-consent key. Query embeddings, when semantic search is enabled, still follow its separate opt-in rule. If retrieval finds nothing, answer synthesis is skipped. If the answer provider is offline, sources remain inspectable.

The existing authenticated API has a narrow `/api/memory-assistant/ask` route. It shares exact-origin checks, session cookies, the 10 KB body ceiling, rate/concurrency limits, no-store headers, and content-free operational logs. Its contract rejects extra evidence fields and more than five records. The server-side configured `OPENAI_MODEL` uses Responses API Structured Outputs, `store: false`, no tools, and a bounded output budget. The answer schema contains evidence sufficiency, individual claims with source Memory IDs, overall source IDs, and unresolved questions. The server revalidates every citation against only the supplied evidence set and rejects malformed or fabricated references; the client validates again. The UI renders each claim with clickable numbered citations and short excerpts read from current local canonical Memories, not model-repeated quotations. Opening a source uses the existing detail flow; View on Timeline opens that same Memory over Timeline.

The model is instructed to preserve uncertain date precision and confidence, surface apparent conflicts, and return insufficient/partial evidence rather than inventing facts. A deterministic warning also flags differently dated, same-titled source records for inspection; it does not decide whether they describe the same event. Citation validation establishes traceability to supplied records, not semantic proof that the model interpreted them correctly; users should inspect sources. An answer is hidden if any of its cited source snapshots no longer match the current canonical records. Ask is read-only and cannot edit archive records. The deterministic development mock makes no paid request. A live Ask smoke test requires separate approval and configured server credentials.
