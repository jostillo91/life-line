# Data model

Production initialization creates an empty local archive and retains existing records; starter fixtures are development-only. GitHub Pages introduces no database schema or archive-format change. Its HTTPS origin has storage separate from localhost, with no automatic migration or cloud synchronization. Full/encrypted Backup & Restore is the explicit transfer path. Hosted assets and service-worker caches contain application resources, never canonical records, media, GPS or semantic vectors.

`Entry` is the central record. It holds immutable `id`, `recordTime`, `createdAt`, and mutable `updatedAt`, alongside references to people, places, tags, media, and related entries. Updating event time never changes record time.

Optional `Entry.deletedAt` is a validated canonical UTC ISO timestamp. Its absence means live, including every existing memory. Soft deletion changes only this metadata, preserves the final pre-delete snapshot and all history, and removes the derived semantic vector atomically. No Dexie schema/index migration is required: schema 8 already stores optional Entry properties. Restore clears it, retains ID/creation/record timestamps and history, advances `updatedAt`, and omits missing supporting references with warnings. An internal `archiveSettings` initialization marker prevents starter memories returning after Empty Trash or an intentionally empty restore; it is not exported profile data.

Quick Capture saves an ordinary `Entry` of kind `memory`, with a local `Untitled memory` fallback and no new table/schema/archive format. Its default event date is `unknown`/`unknown`; approximate years retain a four-digit start (for example `2012`) with approximate precision/confidence, and approximate ages have an age value with no inferred calendar start. Record/creation timestamps are captured when the draft is first opened and survive recovery independently of its event date. The single recoverable local-storage draft is scoped to the archive database, excluded from backups/search/revisions, and cleared after a successful canonical save. Media is imported through the normal binary/metadata service before save; draft discard/detach never deletes original Media. Missing attachment IDs are omitted with a warning at save, never recreated. A newly saved capture has no prior revisions; subsequent meaningful edits use normal history.

Schema 8 adds `memoryRevisions`: `id`, indexed `memoryId`, ISO UTC `createdAt` checkpoint timestamp, `source` (`editor`, `dateMove`, `restore`, `undo`, `relationship`, `media`, `assistantAccepted`, `delete`), `changedFields`, optional editor `checkpointKey`, and an explicit canonical Entry `snapshot`. Compound `[memoryId+createdAt]` supports newest-first paginated reads; `[memoryId+checkpointKey]` indexes session checkpoints. Snapshots include title/body/kind, complete `eventDate`, importance/status, People/Place/Tag/ordered Media/related Memory IDs, notes, and original identity/timestamps. They contain no transient UI state, assistant proposals or binary copies. The history table starts empty on upgrade; the first meaningful change captures the prior saved baseline. `updatedAt`-only saves do not make revisions. Editor session/five-minute coalescing limits duplicate snapshots without pruning meaningful history.

`Archive.revisions` is optional for compatibility and normal UI loading. Explicit JSON/full-backup export includes all revision records and live/deleted canonical memories. ZIP/JSON format v3 preserves deletion state and history; legacy v1/v2 remain readable without generating past states. Merge remaps revision IDs, owners and every snapshot reference safely and deduplicates identical history; Replace swaps incoming history with current canonical data atomically. Historical and deleted-memory references may be unavailable and need not pass live canonical relationship validation. Restoring filters them against available records, reports omissions, and keeps untouched historical snapshots. History restoration preserves current ID/creation/record timestamps, advances `updatedAt`, and adds the current pre-restore state to history first. Recovery Center restoration retains all existing history. Permanent deletion atomically removes the canonical memory, every owned revision and its vector, and detaches incoming related-memory references; Media metadata/files remain. No expiration or automatic history purge exists. See `ARCHITECTURE.md` for checkpoint/retention details.

Database schema version 7 adds `archiveSettings` (`key: 'profile'`, `value: ArchiveProfile`). Optional `Archive.profile.birthDate` is an exact ISO calendar date explicitly chosen by the user, never inferred. It is included in JSON, full ZIP, and encrypted backups. Replace adopts the incoming profile and clears old metadata when absent; Merge preserves a configured local birth date, otherwise adopting incoming profile metadata. Archive format v1 is unchanged and older files remain valid. The migration adds a table without rewriting Memories or Media.

Timeline intervals, clusters, density, label lanes, zoom, focal date, and filters are derived presentation/session state, not new archive entities. Month/year/season/range intervals and approximate markers never rewrite event-date precision or confidence. Age/unknown/incomplete dates remain unpositioned, even with a birth date configured.

`eventDate` separates `precision` (exact, month, year, approximate, range, season, age, or unknown) from `confidence` (confirmed, likely, approximate, guess, unknown). It supports optional start/end ISO values, season, age, and a future display value. People, Places, Tags, and LifeEras are independent reusable records.

Deleting a Person, Place, or Tag removes only that ID from live referencing entries; deleted memories retain unavailable IDs until recovery reports and omits them. New-entry drafts are transient local storage records and never become empty database entries.

Date movement preserves an entry's ID, record timestamp, creation timestamp, content, and relationships. The event-date object is copied whole for undo, retaining precision, confidence, season, range, or age metadata.

`Media` records have stable IDs, type, filename, MIME type, byte size, import time, optional descriptive/capture metadata, and an opaque storage key. Entry `mediaIds` form the relationship; binary files are deliberately excluded from JSON exports. Unattached media remains a future-safe orphan record until explicitly deleted.

The order of `mediaIds` on an Entry is the attachment order. Detaching only removes that relationship, leaving the Media record and binary available for another entry or the Media Library.

Photo Media may also hold a SHA-256 `contentHash`, an accepted `captureDate` with source/confidence/precision, and structured local metadata for original/create timestamps, GPS coordinates, camera make/model, file modification time, and orientation. Date suggestions follow this precedence: EXIF original capture date, embedded create date, conservative filename date, file-modified date, then unknown. Weak file-modified evidence is labeled as such.

Media capture dates and Entry event dates are independent. Importing or attaching a photo never changes an Entry date. A user may explicitly create a Memory from selected photos; that action translates confirmed photo dates into the existing exact/month/range/approximate event-date model for review in the normal editor.

`Media.placeId` is an optional confirmed relationship to an existing `Place`. It is distinct from raw GPS coordinates and from `Entry.placeIds`: clustering only proposes a relationship, assigning a Media Place requires confirmation, and a shared Place across attached media only produces an optional Memory suggestion. Conflicting Media Places produce no recommendation and never modify the Memory automatically.

`Place.address` is optional and separate from its personal `name`. A reverse-geocoding suggestion can fill the address draft only after explicit lookup and selection, and the edited Place is persisted only after Save. Existing Places and archive v1 files remain valid without an address; no Dexie migration is required.

`placeSuggestionIgnored` records that a user dismissed a local GPS cluster without discarding its coordinates. Place coordinates may be initialized from the simple arithmetic center of a reviewed cluster; no street address is invented or stored through this workflow.

The full backup serializes every persistent user-owned record and relationship without changing date precision, confidence, timestamps, attachment order, GPS/EXIF metadata, or Media-to-Place links. Binary originals are external to `data.json` but are mapped by stable Media ID in `manifest.json`. Object URLs, open views, filters, modal state, drafts, and generated thumbnails are not archive data.

Standard backups are ZIP archive format v3, with v1/v2 read compatibility. Manifest counts include `deletedMemories`; `memories` counts all canonical records. Optional encrypted backups contain that same history/deletion-bearing ZIP behind the unchanged version-1 authenticated-encryption container; no private record, revision or media metadata appears outside the encrypted payload. Container salt, IV, KDF identifier, and work factor are non-sensitive decryption parameters. Passwords are never persisted or included in archive data.

`restoreFiles` is a transient Dexie staging table introduced in database schema version 5. It is never exported. Replace restoration fills this table only after ZIP and hash validation, then moves staged blobs into `mediaFiles` in the same transaction that replaces structured records. Lightweight restore history is kept in local storage and never rewrites a Memory's original timestamps.

Life Map center, zoom, visibility switches, and time filter are session-only UI state and are not exported. Successful reverse-geocode suggestions are cached in local storage using rounded coordinates to avoid repeated provider requests; that cache is also not part of the full archive.

Database schema version 6 adds local derived `semanticVectors` and `semanticSettings` tables. A vector is keyed by Memory ID and stores a fingerprint of its selected search text, embedding model, dimension, index version, and numeric values. The enabled setting records only local opt-in. Neither table is canonical archive data or appears in JSON, ZIP, or encrypted backups. Restore invalidates vectors so remapped or replaced Memories cannot retain stale search matches; rebuilding remains an explicit action. Schema upgrade does not change existing Entries, Media, or archive format v1.
